🧮 1. 语义分析：检查 + 翻译（第7章）

🎯比喻：词法分析认单词、语法分析看结构，都像检查一篇文章"每个词是否合法、句子是否通顺"；语义分析则问"这句话讲不讲得通"——"你们是一个优秀的燕大学子"语法没错，但语义不对（量词冲突）。实际编译器里，语义分析通常搭着语法分析的便车一起做（语法制导翻译）。
📏 词法 vs 语法 的"字母"口径（课件导引，易考辨析）：词法分析和语法分析都是对符号串进行分析，区别在于——词法分析识别单词，语法分析识别句子/程序；且两种分析中"一个字母"的含义不同：词法分析中一个字母代表组成单词的一个符号；语法分析中一个字母代表一个单词。

语义分析的两项功能

  • 静态语义检查（编译期）：① 类型检查（操作数类型是否合法、int×real 要不要转换）② 控制流检查（转向点是否合法，如 C 的 goto 不许转入 case）③ 一致性检查（同一作用域标识符只能声明一次）。动态语义检查则发生在运行期（如除零溢出）。
  • 执行翻译：通过检查后翻译成中间代码（第8章）或目标代码（第10章）。
  • 课件另一口径：与语义分析相关的工作 = 静态检查 + 收集语义信息（为语义检查和代码生成等后续阶段收集程序的语义信息，有些内容并入中间代码生成部分讨论）。
📍 语义分析和中间代码生成的逻辑位置（课件 8.2 图示）：词法分析 → 语法分析 → 中间代码生成 → 中间代码优化 → 目标代码优化 → 目标代码生成；静态语义分析在语法分析之后、中间代码生成之前把关（贯穿语义处理）。

属性文法：给文法符号"贴标签、算数值"

🗣️人话版：普通文法只管结构，不管"值"。属性文法给每个文法符号贴便签——记号 X.a 读作"X 身上那张便签 a 上写的值"。语法分析每用一条规则，就顺手按语义规则算几张便签：结构认清的同时，值也算出来了。三元组 A=(G,V,F) 用大白话读：老文法 G ＋ 一套便签 V ＋ 便签怎么算的规则 F。
便签示例：E 的便签 E.val = 27 d 的便签 d.lexval = 3（词法分析早贴好了）

引入属性文法的目的：借助这个工具来说明程序设计语言的语义。在上下文无关文法基础上扩展，形式上是三元组 A = (G, V, F)：G 是上下文无关文法，V 是属性的有穷集合，F 是关于属性的断言（语义规则）的有穷集合。

  • 属性：刻画文法符号我们关心的特性——值、类型、名字、偏移地址、代码片段……记号 X.a（符号X的属性a）。
  • 语义规则：挂在每个产生式上，两种形态——复写规则 X.a := Y.b；语义函数 b := f(c₁,…,cₖ) 或纯动作 f(c₁,…,cₖ)（如 print）。
经典例（表达式求值属性文法，E、T、F 都有属性 val）：
S→E　　　{ print(E.val) }
E→E₁+T　{ E.val := E₁.val + T.val }
E→T　　　{ E.val := T.val }
T→T₁*F　{ T.val := T₁.val × F.val }
T→F　　　{ T.val := F.val }
F→(E)　　{ F.val := E.val }
F→d　　　{ F.val := d.lexval }　（d.lexval 由词法分析给出）

综合属性：由子结点算出父结点（信息自下而上传）。对语法树做自下而上（后序）遍历，遇到能算的就算，就能完成求值。

🧮人话版：综合属性就像手算 3*(5+4)——必须先算最里层括号：有了 5 和 4，才能算出 9；有了 3 和 9，才能算出 27。先有孩子（叶）的值，才有父亲（根）的值，数值从树根往上看是一层层"汇上去"的。从最深处往上算，算到根，答案自然出来。

🎬 属性求值动画：3*(5+4) = ?（课件7.1节原例）

✍️ 静态手算版：前 4 步逐步旁注（先自己算，再看动画对答案）

翻译模式 与 语法制导翻译

  • 语法制导翻译：在语法规则指导下，通过执行语义规则完成对输入串的翻译（第4/6章的分析器走一步，语义动作跟着执行一步）。
  • 翻译模式（Translation Scheme）：另一种描述形式——把语义动作嵌入产生式的具体位置（花括号里），体现"何时调用哪个动作"的翻译算法。

YACC：分析器自动生成工具（7.3节）

YACC（Yet Another Compiler-Compiler）根据文法+语义动作自动生成 C 语言写的语法分析器，与词法分析器生成工具 Lex 配合：两者生成的 C 程序一起编译成编译器。正是"语法制导翻译"思想的工业化落地。

🗂️ 2. 符号表：编译器的"户口本"（第8章）

🎯比喻：符号表就是编译器的户籍管理处——程序里每个名字（变量、常量、过程）都要来登记；用的时候查一下；写错了（重名、未登记就使用）它负责报警。

符号表的功能（三句话，简答必背）

🗂️先看一张真的长什么样：写了 int a; real x; 之后，表里就多两行——a｜int｜…地址、x｜real｜…地址。名字栏是钥匙，信息栏记属性；查表=按名字找到这行、读后面几栏。下面的一切功能，都是围绕这张表的"登记、查验、按表分房"。
  1. 收集符号属性（标识符、常量、变量、过程、函数等）；
  2. 作为上下文语义合法性检查的依据（如 a:=b+c 的类型检查）；
  3. 作为目标代码生成阶段地址分配的依据（看类型定大小和地址）。

它贯穿编译全过程：词法/语法阶段不断更新，语义分析阶段写入属性，代码生成阶段读取。PL/0 词法分析（线性表实现）就在用它。

组成与常见属性

符号表 = 名字栏（主栏，内容叫关键字 keyword） + 信息栏（多列，含许多子栏和标志位）。常见属性：① 符号名（按名存取，不能重名）② 类别（常量/变量/过程/函数）③ 类型（类型检查依据）④ 存储信息（地址）⑤ 作用域（全局/局部）⑥ 其他（数组内情向量、记录成员、形参等）。

符号表总体结构的设计取决于：① 源语言的复杂性（词法、语法结构的复杂性）② 对编译系统时间效率和空间效率的要求。

五类操作 与 实现数据结构

操作：① 查询名字是否已在表中 ② 插入新名字 ③ 访问某名字的信息 ④ 填写/更新信息 ⑤ 删除无用项。

结构特点
线性表（无序）简单，PL/0 采用
有序表可折半查找
栈符号表适合嵌套作用域
Hash 表查找快，实用编译器主流

静态语义检查与"声明/使用"查错

静态检查是代码生成前合法性检查的最后阶段，包括：控制流检查（break 必须有合法包围）、唯一性检查（枚举元素不重复）、名字上下文相关性检查、类型检查。

查错流程（简答模板）：
遇新声明 → 查符号表：已有同名 ⇒ 重复声明错误；没有 ⇒ 登记属性入表
遇使用 → 查符号表：查无 ⇒ 未声明错误；查到 ⇒ 取属性做进一步分析

🏭 3. 中间代码：先译成"世界语"（8.3节）

为什么要中间代码

优点：① 与机器无关，便于移植（换目标机只换后端）② 对中间代码做优化比在源/目标代码上做更容易。缺点：多了一级翻译。总体优大于缺。（注意：PL/0 没有中间代码生成阶段。）

常见形式：AST 抽象语法树 ｜ TAC 三地址码（四元式）｜ P-code（Pascal 用）｜ Bytecode（Java→JVM）｜ SSA 静态单赋值。

四元式（本关主角）

🗣️人话版：四元式就是一张三地址便条，四个格子问四件事：拿谁、对谁、做什么运算、结果放哪。一行只干一件事；复杂表达式拆成几张便条接力，先写的先算，临时变量 T₁、T₂ 就是接力棒。
玩具版只有一条：a+b ⇒ (+, a, b, T₁)——就这么简单，难的只是式子更长、要按"先乘除后加减"排好出条的顺序。
四元式 = （算符 op，左操作数 ARG1，右操作数 ARG2，结果 RESULT）
例（X 为整型、0.618/Y 为实型，先做类型转换）：Z := X + 0.618*Y ⇒
(1) ( inttoreal, Y, -, T₁ )　　把 Y 从整型转成实型
(2) ( *, 0.618, T₁, T₂ )
(3) ( +, X, T₂, Z )

✍️ 手算示范：Z := X + 0.618*Y 逐条旁注

#写出的四元式【旁注】为什么是它
1( inttoreal, Y, -, T₁ )类型对齐：X 整型、0.618 实型，先把 Y 转实型放 T₁；一元运算没有右操作数，写 "-" 占位
2( *, 0.618, T₁, T₂ )先乘除：0.618×T₁ 最先算，结果用接力棒 T₂ 传下去
3( +, X, T₂, Z )后加减：X+T₂ 才算；最终结果有名字 Z，就不用再借临时变量了
